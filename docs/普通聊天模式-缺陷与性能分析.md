# 普通聊天模式 — 缺陷与性能分析

> 分析日期：2026-07-27
> 分析范围：默认单模型聊天链路（**不含** 多模型 / 辩论 / 翻译 / 媒体生成 / 智能体模式）
> 方法：4 路并行静态代码审计（发送与流式主链路、数据层与 LLM 适配器、UI 渲染与滚动、Riverpod 状态与生命周期），全部结论附 `文件:行号` 证据

---

## 0. 总体结论

这条链路的整体工程质量不低。以下机制经逐一核对**实现正确**，不构成问题：

- SSE 解码（`sse_decoder.dart`）：多字节字符、跨 chunk 事件边界、CRLF、多行 data 处理均正确
- tool_call 增量合并：OpenAI `index` 键 / Anthropic block index / Responses `output_index` 边界处理正确
- 多 Key failover：以 `committed` 标志保证首 chunk 之后不再重试，不会产生重复消息（`turn_stream_binder.dart:545-548, 971`）
- HTTP 超时与取消：`dio_client.dart:21-23`（connect 30s / receive 5min），取消经 `llm_cancel_bridge.dart` 正确桥接到 dio CancelToken
- 状态不可变性：`ChatState` / `ChatMessageView` 全部 freezed，`_replace`/`_emit` 均先拷贝列表，无就地 mutate
- UI 渲染优化：orderKey select 隔离列表重建、每气泡 select + Expando 索引、流式分块 memo、DeferredContent 分帧、稳定 key + `findChildIndexCallback`、控制器均正确 dispose
- 序列化：block 经 freezed union + `fallbackUnion: 'unknown'`，未知类型降级不丢行；`model_converters.dart` 双向对称

**缺陷集中在两类**：

1. **异步窗口缺少守卫** —— 检查条件与状态置位之间隔着大量 `await`，或后台流与话题增删改并发时无互斥。
2. **流式期间的重复全量计算** —— 每个 delta 对全文重做 O(n) 工作，整条流退化为 O(n²)。

## 1. P0 — 数据丢失

### P0-1 「继续生成」会抹掉消息已生成的前半段

| 项 | 内容 |
|---|---|
| 类型 | bug / 数据丢失 |
| 影响 | UI 与数据库中原有内容被物理删除，不可恢复 |

**根因链**

1. `chat_controller.dart:1052-1093`（`continueGenerating`）调用 `_streamInto` 时只传新的 `continuationBlockId`，`leadingBlocks` 用默认空值 —— 原消息已落盘的 main_text / thinking / tool 块没有带入本轮。
2. `turn_stream_binder.dart:286`：`completed = [...leadingBlocks]`，本轮累积块因此只有续写内容。
3. checkpoint 与终态落盘都走 `persistMessageBlocks`（`interrupted_settlement.dart:14-35`）→ `replaceMessageBlocks`，其实现为**先删光该消息所有块再写入**（`chat_repository_impl.dart:287-292`：`deleteByMessageId` → `upsertAll`）。
4. 首个 checkpoint（`turn_stream_binder.dart:425-443`，2 秒后触发）执行时原内容即被删除；UI 侧 `update()`（:368-371）的 `aggregateText` 同样只含续写文本。

代码注释 `chat_controller.dart:982-983` 写的是 "The new content is appended to the existing blocks (not replacing them)"，与实现相反。

**复现步骤**

1. 设置很小的 maxTokens
2. 发送让模型输出长文，触发截断，出现「继续生成」按钮
3. 点击「继续生成」
4. 约 2 秒后观察气泡：原有前半段文本消失，仅剩续写内容；重启 App 后 DB 中同样只有续写段

**修复建议**

`continueGenerating` 中先 `await _repo.getMessageBlocksByMessageId(messageId)`（按 `message.blocks` 排序），作为 `leadingBlocks` 传入 `_streamInto`。

## 2. P1 — 可复现 bug

### P1-1 流内错误被静默吞掉：表现为「秒回空白且状态正常」

**Anthropic** —— `anthropic_adapter.dart:162-214`
事件 switch 只处理 `message_start` / `content_block_start` / `content_block_delta` / `message_delta`。流中途的 `event: error`（如 `overloaded_error`、超长上下文在流开始后被拒的 `invalid_request_error`）落入 switch 后无分支命中，循环继续直到服务端关流，随后正常 `yield LlmStreamChunk.done(...)`。

**OpenAI 兼容** —— `openai_compatible_adapter.dart:117-187`（Chat Completions）、`:279-349`（Responses）
Chat Completions 循环只读 `choices` / `usage`，不检查顶层 `error` 键。而 OpenRouter、one-api 类中转、自建代理在限流 / 余额不足 / 上游 5xx 时，正是以 **HTTP 200 + SSE `data: {"error":{"message":...}}`** 返回。Responses 分支同样缺 `response.failed` / `response.error` / `error` 分支。

**用户视角**：回复瞬间「完成」、内容完全空白、消息状态为 success、无任何错误提示。极易被误判为模型或网络问题。

**复现**：用 OpenRouter 免费额度触发限流，或任一中转站余额不足时发送消息。

**修复建议**：两个适配器的事件循环中检测错误载荷（Anthropic 加 `case 'error':`；OpenAI 检测 `json['error']` 及 Responses 的 `response.failed`），抛出携带 message 的 Failure，交由 `turn_stream_binder` 的错误路径接管。

### P1-2 快速连发竞态 → 同话题双流并发，且「停止」失效

**根因**

- `send()` 在 `chat_controller.dart:412-413` 读 `state.value.isStreaming` 做守卫，但 `isStreaming=true` 要到 `:540` 的 `_emitTurn(topicId, views, streaming: true)` 才生效。
- 两者之间有大量 `await`：拦截器（:407）、`appCurrentModelProvider`（:456）、`_ensureTopic`（:459）、4 次以上 DB 写入（:491-521）。慢设备 / 慢 DB 上窗口可达数百毫秒。
- 第二次 `send()` 在窗口内进入时守卫仍看到 `isStreaming=false` → 用户消息被写入两次，两个 assistant 占位并发流式。

**连带放大**：两条流各自 `bindToken`（`turn_stream_binder.dart:494`）。先结束的一条走 `emitTurnEnd` → `registry.finish(topicId)`（`streaming_registry.dart:66-73`），该方法**整体移除话题的 token 列表和 streaming 状态**。仍在跑的第二条流从此无法取消（`cancel` 在 :83-84 因 `_tokens[topicId] == null` 直接 return），绿点提前消失，`isStreaming` 变 false 后用户还能触发第三次发送。

**复现**：用物理回车键或连点发送按钮（UI 禁用依赖同一个异步 state）→ 同一句话出现两条用户消息、两个回复气泡；等其中一条完成后按「停止」，另一条停不下来。

**修复建议**

- `send()` / `regenerate()` / `resend()` 入口改用控制器内的**同步**布尔标志（或直接检查 registry 中该 topic 是否已 streaming）做守卫
- `StreamingRegistry.finish` 改为按 token / 流计数，最后一条流结束时才清除话题条目

### P1-3 ChatController 为 autoDispose → 退出聊天页即打断流式并永久泄漏

**根因**

- `chat_controller.g.dart:68`：`isAutoDispose: true`
- 整套「后台流式」设计（`streaming_registry.dart` keepAlive + `_emitTurn` 按 topic 路由）只在**切话题**时成立——provider rebuild 不销毁 notifier。
- 但一旦 ChatPage 从树上移除（返回上级路由 / 被替换），控制器销毁。`TurnStreamBinder` 的下一个 chunk 触发 `_emitTurn` → `_registry` → `ref.read`（`chat_controller.dart:111-112`）抛 "ref used after dispose"；异常进入 `on Object catch`（`turn_stream_binder.dart:948`）后走 `_persistMessageBlocks` → `_repo` → 又是已销毁的 `ref.read` → 二次抛出未捕获。

**后果**

1. 流中断、部分内容丢失，消息滞留 streaming 状态（只能靠下次打开时 `_settleInterruptedMessages` 兜底）
2. `registry.finish(topicId)` 永不执行 → `liveByTopic` 条目与 `_tokens` 永久滞留（`streaming_registry.dart:56-73`），话题列表绿点常亮
3. `StreamingKeepAliveService.end()` 不会调用 → 前台保活服务 / 通知永不结束

**复现**：发送一条长回复 → 流式过程中把 ChatPage pop 掉或替换根路由 → 观察异常与永不消失的「生成中」标记。

**修复建议**：流式期间 `ref.keepAlive()`（onDone/onError 时释放）；或把 `streamInto` 的依赖在 turn 开始时快照，不再穿透 controller 的 Ref，收尾只依赖 keepAlive 对象。

---

### P1-4 删除 / 清空正在后台流式的话题 → 已删数据被 checkpoint 复活

**根因**：`topics_providers.dart:236-261`（`delete`）与 `:327-343`（`clearMessages`）完全不检查 `streamingRegistryProvider.isStreaming(id)`，也不调用 `registry.cancel(id)`。后台流继续运行，每 2 秒的 checkpoint（`turn_stream_binder.dart:425-443`）和终态 `_persistMessageBlocks` 将已删除话题的 message / blocks 重新写回 DB，产生孤儿数据；话题列表绿点仍指向已删话题。

**clearMessages 额外表现**：`bump()` 触发 `build()` 重跑，但 `chat_controller.dart:331` 优先取 registry 的 liveViews → 清空后界面仍显示旧对话全量消息，直到流结束。

**复现**：话题 A 发送长回复 → 切到话题 B → 在侧栏删除 / 清空 A → 检查 DB 中 A 的 message 行数（会重新出现）。

**修复建议**：删除 / 清空前先 `registry.cancel(id)` 并等待 finish；或在生成中直接拒绝操作并提示。

---

### P1-5 冷启动竞态导致话题串台

**根因**：`sidebar_selection_providers.dart:20-37`（`CurrentAssistantId`）与 `:45-64`（`CurrentTopicId`）的 `build()` 返回 `null` 后异步 `_hydrate()` 从 DB 读回上次选择并**无条件**写入：

```dart
Future<void> _hydrate() async {
  final stored = await ref.read(chatRepositoryProvider).getSetting(kCurrentTopicSettingKey);
  if (stored != null && stored.isNotEmpty) state = stored;   // 无「用户已手动选择」守卫
}
```

同文件的 `SidebarTabIndex`（`:73-89`）有 `_touched` 标志专门防这个竞态 —— 说明作者已意识到问题，但这两个 provider 漏掉了。

**复现**：冷启动 App → hydrate 完成前立刻新建话题（`Topics.create` 会 set `currentTopicIdProvider`，`topics_providers.dart:59`）或点选另一话题 → hydrate 完成后 state 被旧话题 id 覆盖 → 视图跳回旧话题。若用户已开始输入 / 发送，消息会落到用户看不到的话题（串台）。

**修复建议**：仿照 `SidebarTabIndex` 增加 `_touched` 守卫，`set()` 中置位，hydrate 仅在未触碰时写入。

---

### P1-6 停止按钮在工具执行 / 确认弹窗期间不生效

**根因**：`stopStreaming`（`chat_controller.dart:283-287`）只做 `token.cancel()`，中断的是 HTTP 流。但当流已结束、正处于 `await runRoute()`（`turn_stream_binder.dart:842/847`）或 `await confirm.request(...)`（:831-839）时，没有任何代码检查 `cancelToken.isCancelled`；`rejectAll()` / `cancelAll()` 只在 `persistStopped`（:473-474）和终态错误路径（:981-982）执行。

**后果**：停止后长时间运行的工具继续跑完；若正卡在确认弹窗，取消要等用户对弹窗做出选择后才发生，期间 UI 一直显示 streaming。

**修复建议**：工具循环内每轮开始、每个工具执行前后检查 `isCancelled`，命中即走 `persistStopped`；`stopStreaming` 同时调用 `rejectAll()` / `cancelAll()`。

## 3. P1 — 性能

### PERF-1 流式期间输入栏每个 token 全量重建 ⭐ 性价比最高

`chat_input_bar.dart:263`：

```dart
final isStreaming = ref.watch(chatControllerProvider).value?.isStreaming ?? false;
```

直接 watch 整个 `AsyncValue<ChatState>`，流式每个 delta 都会重建 `_ChatInputBarState.build` 整棵子树，包括重新构造 `InputBoxComposer`、`ChatInputActions(ref, ...)`（:287）。气泡侧精心设计的 select 隔离被这一处整体抵消。

同文件 `:246-255` 另有四个裸 `ref.watch`（inputMode / clearConfirm / mcp / parameter），频率低，可顺带收紧。

**修复**：`ref.watch(chatControllerProvider.select((a) => a.value?.isStreaming ?? false))` —— 一行改动。

---

### PERF-2 代码块高亮在流式期间退化为 O(n²)

- `code_block_body.dart:244-255`：PerLineCodeView 流式 debounce（50ms）后调 `_highlightAllLines()`；`:259-267` 对**整段**代码 `highlight.parse`，非增量
- `:411-419`：SelectableHighlightView 同样全量 reparse
- `:287-334`：build 中 `List.generate(widget.lines.length, ...)` 每行一个 Row + Text.rich，Column 无懒加载
- `parseToSpans` 的 LRU 缓存（`code_highlight_utils.dart:12-41`）对流式完全无效——每个 delta 都是新 key，还会把 128 条缓存冲刷掉

**触发场景**：回复含 1000+ 行代码块且开启自动换行时，流式期间每 50ms 对全文重新高亮，单次 parse 即可超出 8ms 帧预算。

**修复建议**：流式路径改用文件内已有但未被使用的增量 `LineHighlighter`（`code_highlight_utils.dart:67-113`），只 parse 新增行；流式中跳过 `_spanCache` 写入；超长代码考虑仅高亮可视区。

---

### PERF-3 图片缓存无上限、无解码尺寸限制

- `media_blocks.dart:20-29`：`_imageProviderCache` 全局 Map 按 block.id 缓存 `MemoryImage`，**永不淘汰**
- `:78-87`：`Image(image: provider)` 无 `cacheWidth` / `ResizeImage`，仅有 `maxHeight: 300` 的布局约束

一张 4000×3000 图为渲染 300px 缩略图要解码约 48MB 位图，且原始字节常驻。

**修复建议**：改用 `ResizeImage(provider, width: 逻辑宽 × dpr)`；缓存加 LRU 上限或改挂 Expando。另 `NetworkImage`（`:51-53`）无磁盘缓存，建议 `cached_network_image`。

---

### PERF-4 打开话题：2N 次全量反序列化 + N+1 块查询，且无分页

- `chat_controller.dart:347`：`getBranchMessages` → 内部 `chat_repository_impl.dart:74` 全量 `getByTopicId`
- `chat_controller.dart:350`：紧接着**再次** `getMessagesByTopicId`，第二次全表段扫描 + 整 blob JSON 反序列化
- `message_view_projector.dart:48`：每条消息一次 `getMessageBlocksByMessageId`，串行 await

索引本身齐全（`messages_table.dart` 的 topic / parent 索引），瓶颈在访问模式。长话题（数百条消息）每次切话题 / 删消息 / 切分支都是 O(N) 次串行 DB 往返。

**修复建议**：复用 `getBranchMessages` 返回值免去第二次查询；blocks 改为 `messageId IN (...)` 一次批量取回后内存分组；考虑窗口化加载。

## 5. 建议修复顺序

1. **P0-1**（继续生成数据丢失）—— 唯一造成不可恢复数据丢失的问题
2. **P1-1**（流内错误静默）—— 用户最易误判、投诉成本最高
3. **PERF-1**（输入栏 select）—— 一行改动，立竿见影
4. **P1-2 + P1-3**（发送竞态 + autoDispose 生命周期）—— 二者都涉及「流的所有权」，建议一起重新设计：让 turn 的生命周期归 `StreamingRegistry` 所有，controller 只做视图投影
5. **P1-4 + P1-5**（话题增删与流的互斥、hydrate 守卫）
6. PERF-2 / PERF-4（流式高亮增量化、话题加载批量化）
7. P2 清单按迭代余量处理
